# src/ — TypeScript source of the everything-search-mcp server

DOX local contract for `src/`. Parent: [`AGENTS.md`](../AGENTS.md). Closer doc wins on local detail; nothing here may weaken DOX.

## Purpose
- Complete source tree of the npm-published MCP server (`package.json:8` maps `bin` to `dist/index.js`; `dist/` is produced from this folder only, per `tsconfig.json:7`).
- Entry point `src/index.ts` wires the MCP stdio server and the three exposed tools (`search_files`, `get_file_info`, `check_status`).
- Dispatch and security layers (`search/`, `utils/`) sit between the server and the per-OS shell wrappers (`platform/`).

## Ownership
- This subtree owns: `src/index.ts` (server registration, tool schemas, handler, response/error shape), `src/tool-args.ts` (the zod 4 argument gate each tool call passes through), `src/search/unified.ts` (platform routing), `src/utils/` (platform detection, validation), `src/types/index.ts` (shared interfaces), `src/platform/*.ts` (OS command construction and output parsing).
- Owned by the parent/root scope: `package.json` and its scripts, `tsconfig.json`, the vendored `bin/es.exe` and `scripts/download-es.js`, `tests/`, and npm publishing.

## Local Contracts
- Server identity: `new Server({name: 'everything-search-mcp', version: '1.0.0'})` at `src/index.ts:14-24`. Unfixed drift: version is hardcoded `1.0.0` (`:17`) while `package.json:3` is `1.1.0`.
- Tools are declared in the unchanged `src/index.ts:26-105` (input schemas) and handled in the single `CallToolRequestSchema` handler `src/index.ts:113-260`, with `ListTools` at `:107-111`; `main()` connects `StdioServerTransport` at `src/index.ts:262-267` and is invoked at import time (`:269`).
- stdout is the MCP protocol channel: all logging goes to `console.error` (`src/index.ts:243`, and `main().catch` at `src/index.ts:269-272`). Never write to stdout from this subtree.
- Argument gate (binding): every tool call passes through the zod 4 schemas in `src/tool-args.ts` (53 lines) before the handler reads them — `parseSearchFilesArgs` at `src/index.ts:119` (`SearchFilesArgsSchema` `:6-16`), `parseGetFileInfoArgs` at `src/index.ts:171` (`GetFileInfoArgsSchema` `:18-20`); `check_status` takes no arguments and has no gate. `toolArgumentSchemas` (`:22-25`) is the tool→schema map. `src/index.ts:10` is this import; the previously unused `import { z } from 'zod'` is gone.
- Gate scope (deliberate split): `src/tool-args.ts` does type/presence/coercion/unknown-key-stripping only; length, range and content rules stay in `src/utils/validation.ts`, so its codes (`QUERY_TOO_LONG`, `PATH_TRAVERSAL`, `HOME_PATH_NOT_ALLOWED`, `INVALID_CHARACTERS`, `PATH_TOO_LONG`) keep firing from the same call sites. `parseArgs` (`:32-45`) throws `ValidationError` with `code: 'INVALID_ARGUMENTS'` and message `Invalid arguments for <tool>: <dotted issue paths>`. The module has no side effects, so tests import it without booting the stdio server (`src/index.ts:269` runs `main()` at import time).
- Gate behavior (binding): rejects missing/non-string `query`, missing/non-string `path`, and non-numeric strings for `maxResults`/`offset` — cases that previously surfaced as `UNKNOWN_ERROR` from a `TypeError`. Everything the server accepted before still passes: numeric strings coerce (`"50"`→50, `""`→0, `true`→1, `[]`→0), `0`/`-1`/`5000`/`200000` pass through unclamped because clamping is the adapter's job (`windows-cli.ts:67`, `darwin.ts:12`, `linux.ts:12`), `null` stays `null` so the handler's `?? 100` / `?? 0` defaults apply (`.nullable()` is load-bearing), out-of-enum `sortBy`/`sortOrder` and truthy non-boolean flags reach the adapter fallbacks untouched — the `|| 'name'` fallback (`windows-cli.ts:100`), the `=== 'descending'` test (`:103`) and the truthiness checks (`:71-87`), including the known bug that `matchCase:"false"` enables `-case` — and unknown keys are stripped, as the schemas are not `.strict()`.
- The remaining `as` casts at `src/index.ts:120-128` (e.g. `sortBy` at `:123`) are ungated on purpose: after `parseArgs` they read already-typed values, and the adapter defines the fallback behavior for anything the gate lets through.
- Error shape (binding): every tool response is JSON in a single `text` content item. Success: `{success: true, ...}` (`search_files` keys `src/index.ts:153-163`). Failure: the catch block at `src/index.ts:228-259` returns `{success: false, error, errorCode, tool}` with `isError: true`; `errorCode` comes from `error.code` if present (`src/index.ts:234-236`), else `'UNKNOWN_ERROR'`. `ValidationError` carries `code` and `statusCode` (`src/utils/validation.ts:1-10`), so its code surfaces as `errorCode`; the gate throws that same class, so the codes now include `INVALID_ARGUMENTS` next to the `validation.ts` ones and the `catch` block itself needed no edits — the published envelope is unchanged.
- Security boundary (binding): all shell-bound query/path input passes through `src/utils/validation.ts` before reaching a subprocess — `sanitizeShellArg` (`validation.ts:21`), `validateSearchQuery` (`:37`), `validatePath` (`:60`) — enforced inside each platform module (`src/platform/windows-cli.ts:64,151`, `src/platform/darwin.ts:10,84`, `src/platform/linux.ts:10,96`). Caps live in `SecurityConfig` (`validation.ts:12-19`).
- `validateSearchOptions` (`validation.ts:95`) is exported and unit-tested but not called from `src/`; result caps are instead applied per platform via `Math.min(options.maxResults ?? 100, SecurityConfig.MAX_RESULTS)` (`windows-cli.ts:67`, `darwin.ts:12`, `linux.ts:12`).
- Platform routing is centralized in `src/search/unified.ts` using `isWindows/isDarwin/isLinux` from `src/utils/platform.ts:10-20`; `process.platform === 'win32'` maps to `'windows'` (`platform.ts:5`) and anything not darwin falls back to `'linux'` (`platform.ts:7`).
- Sibling boundary (binding): each module in `src/platform/` must keep the same exported triad `searchFiles(options: SearchOptions): Promise<SearchResult[]>`, `getFileInfo(path: string): Promise<FileInfo>`, `getStatus(): Promise<PlatformStatus>` (`windows-cli.ts:62,149,195`; `darwin.ts:8,82,121`; `linux.ts:8,94,132`); `unified.ts:1-10` imports exactly these.
- Windows executes the vendored CLI at `bin/es.exe`, resolved relative to the compiled module (`src/platform/windows-cli.ts:8-11`); the binary itself is root-owned.

## Work Guidance
- ESM-only (`package.json:6` `"type": "module"`): every relative TS import carries the `.js` extension (`src/index.ts:10-11`, `src/search/unified.ts:1-11`, `src/platform/windows-cli.ts:5`). Shared data shapes are imported type-only from `../types/index.js` (`src/index.ts:12`, `windows-cli.ts:6`, `darwin.ts:3`, `linux.ts:3`, `unified.ts:11`).
- `tsconfig.json` is `strict: true` with `target/module ES2022` and `moduleResolution: "bundler"` (`tsconfig.json:2-15`, `include` `:17`, `exclude` `:18`); `include` is `src/**/*` only, so `tests/` is not typechecked by `npm run build`. `forceConsistentCasingInFileNames` was deleted under TypeScript 7 (it is always on there); `types: ["node"]` (`:15`) is deliberately kept because TS 7 changed the default to `[]` and dropping it would remove Node globals from `src/`.
- Adding or changing a tool touches the same chain: schema in the `src/index.ts:26-105` literal, the zod gate in `src/tool-args.ts` (`toolArgumentSchemas` + a parse call), the `CallToolHandler` branch in `src/index.ts`, pass-through in `src/search/unified.ts`, and the triad in each `src/platform/*.ts` that supports it.
- No formatter or lint config exists in the repo; match the style of the neighboring file rather than inventing conventions.
- New security limits belong in `SecurityConfig`/`validation.ts`, not duplicated per platform module.

- `npm test` = `vitest run` (`package.json:28`) under vitest 5.0.4: 81/81 across the three files (`tests/security.test.ts` 22, `tests/integration.test.ts` 22, `tests/tool-args.test.ts` 37 — the last imports `src/tool-args.js` directly, which is why the gate module has to stay side-effect free). The `<100ms` perf asserts at `tests/integration.test.ts:323,335,347` held over 20 consecutive runs and were not loosened.
- `npm run build` = `tsc` (`package.json:24`) under TypeScript 7.0.2: `rm -rf dist && npm run build` exits 0 and emits a dist file set identical to the TypeScript 5.9.3 clean rebuild plus the four new `dist/tool-args.*` artifacts (32 → 36 files); the `#!/usr/bin/env node` shebang survives at `dist/index.js:1`, so the `bin` shim (`package.json:8`) still works. With `declaration: true` the build is also the check that `src/types/` changes compile for consumers. `dist/index.js` contains no zod import — `dist/tool-args.js` is the only runtime zod consumer. `npm pack --dry-run` lists 42 files.
- The suite covers `src/utils/validation.ts` and `src/tool-args.ts` only. There is no vitest config, no lint, no formatter, and the `rg`/`mdfind`/`locate`-dependent code in `src/platform/` plus the routing branches in `src/search/unified.ts` have no automated coverage — on this (Windows) machine only the `es.exe` path can even run.
- The MCP surface itself (the `CallToolHandler`, its envelope, `tools/list`) is verified by a manual stdio JSON-RPC probe of `node dist/index.js` — 35 assertions covering `initialize`, `tools/list` with the three tools, and `tools/call` for valid, retained, gated and security cases. The probe ran from a temp directory and is NOT a committed harness.
- Adapter-side defects that shape what this layer can report are recorded in [`platform/AGENTS.md`](platform/AGENTS.md): Windows `search_files` loses the `ValidationError.code` so a security code reaches the envelope as `UNKNOWN_ERROR`, and `get_file_info` can never succeed on Windows.
